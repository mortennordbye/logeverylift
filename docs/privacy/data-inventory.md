# Personal data inventory

The record of processing (GDPR Art. 30) for LogEveryLift, and the source the privacy policy (`src/app/privacy/page.tsx`) is written from. When a change adds, moves or shares personal data, update this file and the policy in the same PR, and bump `LEGAL_VERSION` (`src/lib/constants/legal.ts`) so users are told. Raise `CONSENT_VERSION` too only if they must accept the change again. The `privacy-compliance` skill (`.claude/skills/privacy-compliance/SKILL.md`) has the checklist.

Facts last checked 2026-10-25.

## Data in the database

All tables live in the app's Postgres in the homelab (Norway). Every user-owned table cascades on user deletion, and `collectUserData` (`src/lib/account-data.ts`) exports all of them; `src/__tests__/integration/account-data.test.ts` fails if a table hanging off `user` is missing from the export.

## Outside the database

- **Server logs** (Loki in the homelab): 7 days. Rate-limit warnings in `src/app/api/auth/[...all]/route.ts` include the client IP. Server Actions log ids and short tags only, never names, emails or request bodies (CLAUDE.md, Safety rules).
- **Request traces** (Tempo in the homelab): 24 hours. Timings of each request, the route and path (which can hold record ids), outgoing API calls by host and path, and database query text with placeholders, never the values. Alloy removes query strings and client IP addresses before they are stored. No names, emails, notes or request bodies (`src/instrumentation.ts`, the homelab's `k8s/talos/infra/loki/alloy-values.yaml`).
- **Backups:** daily `pg_dump`, kept 30 days on the homelab NAS; off-site copy to Google Drive by Synology Hyper Backup, client-side encrypted, Smart Recycle up to 30 versions. The policy promises rotation within 90 days.
- **Browser** (`src/lib/utils/local-data.ts` lists what survives sign-out): session cookie and its 5-minute cache cookie; localStorage `activeWorkout`, `restTimerEnds`, `workoutOverrides`, `workoutReadiness`, `pendingMutationQueue`, `ai_generating`, `ai_pending_edit`, `ai_pending_error`, `weeklyGoal`, admin backups, and display settings (`theme`, `accentColor`, `customAccentHex`, `uiScale`); sessionStorage `staleBundleReloads` (a count of reloads after a deploy and the time of the last one, no personal data, gone when the tab closes; `src/lib/utils/stale-bundle.ts`); service worker caches. All strictly necessary, so no consent banner (ekomloven §3-15). `clearLocalUserData` empties everything but display settings on sign-out and deletion; it leaves `staleBundleReloads`, which is not tied to the account.

## Access by the operator

The admin can read the database and impersonate users (Better Auth admin plugin); impersonated sessions carry `impersonatedBy`. Disclosed in the policy as support and debugging only. The consent gate (`needsTermsConsent` in `src/lib/consent.ts`) never shows to an impersonating admin.

## Data subject rights in the app

- Access and portability: Account → Download My Data (`exportMyData`).
- Erasure: Account → Delete Account (Better Auth `deleteUser`; `handOverSharedCustomExercises` runs first).
- Rectification: in-app editing.
- Withdraw AI consent: Account → AI editing (`setAiConsent`).
- Everything else by email, answered within one month.
